# Technical Explanation Guide

Use this reference when explaining technical concepts, code, software systems,
architecture, AI/ML, LLMs, APIs, databases, networking, infrastructure,
algorithms, mathematics, configuration, or engineering concepts.

The objective is not merely to provide the correct technical answer.

The objective is to help a person who may be new to the subject build an
accurate mental model without losing important technical information.

---

# Core Principle

Simplify the explanation.

Do not simplify away the mechanism.

Prefer:

```text
Simple idea
    ↓
Mental model
    ↓
Journey from start to finish
    ↓
Why each step happens
    ↓
Actual technical mechanism
    ↓
Concrete example
    ↓
Important details and exceptions
```

The user should first understand the idea intuitively and then understand how
it actually works technically.

---

# 1. Establish the Problem Before the Technology

Before explaining a technology, explain what problem caused people to need it.

For example, instead of starting with:

```text
KV cache stores keys and values generated by attention layers.
```

first establish the problem:

```text
An LLM generates one token at a time.

Without caching, every time a new token is generated, the model would have to
recalculate information it already calculated for earlier tokens.

KV cache exists so that this previous work can be reused.
```

Then introduce the technical mechanism.

The user should know:

```text
Problem
↓
Why the problem matters
↓
Technology introduced to solve it
```

before learning implementation details.

---

# 2. Start With the Big Picture

Start substantial explanations by establishing:

* what the thing is
* why it exists
* what problem it solves
* where it sits in the larger system
* what goes into it
* what eventually comes out

Keep this section short.

Its purpose is orientation, not completeness.

---

# 3. Assume the Reader May Be New

Do not assume the user already understands prerequisite terminology.

If an explanation depends on a concept that has not been established, explain
that concept first.

For example, before deeply explaining:

```text
LoRA rank
```

the user may first need to understand:

```text
model weights
↓
weight matrices
↓
fine-tuning
↓
weight updates
↓
low-rank representation
```

Do not force the user to understand a later concept before the earlier concepts
have been introduced.

---

# 4. Use Progressive Detail

Teach difficult topics in layers.

## Layer 1 — Intuition

Explain the idea in everyday language.

Avoid unnecessary jargon.

The user should understand the purpose of the concept.

## Layer 2 — Mental model

Give the user something they can picture.

This may be:

* a pipeline
* a memory system
* a request journey
* a factory-like process
* a small diagram
* an analogy

Do not let an analogy replace the real mechanism.

## Layer 3 — Journey

Explain what happens from beginning to end.

Show the order in which components participate.

## Layer 4 — Actual mechanism

Introduce proper terminology and implementation details.

## Layer 5 — Numbers and examples

Use a small realistic example.

## Layer 6 — Nuances

Explain limitations, trade-offs, exceptions, and edge cases.

Each layer should add precision.

---

# 5. Explain Technical Terms When They First Appear

Use this format:

```text
Technical term — simple meaning
```

For example:

```text
Token — a small unit of text that the model processes.

Embedding — a numerical vector representing information about a token.

Logit — the model's raw score for how likely a possible next token is.

Quantization — representing model values using fewer bits so that the model
uses less memory and often runs faster.
```

After defining the term once, use the real technical term normally.

Do not permanently replace real terminology with an analogy.

The user should learn the vocabulary used in documentation, code, papers, and
engineering discussions.

---

# 6. Explain the Journey From Start to Finish

Whenever the system has a process, explain it in execution order.

For example:

```text
User writes prompt
      ↓
Tokenizer converts text to token IDs
      ↓
Token IDs become embeddings
      ↓
Transformer layers process them
      ↓
Model produces logits
      ↓
Sampling chooses a token
      ↓
Token is appended
      ↓
Process repeats
```

Then explain each stage.

Do not start with the middle of the pipeline unless the user specifically asks
about only that part.

---

# 7. Explain Cause and Effect

Do not merely list steps.

Explain why one step leads to another.

Prefer:

```text
The tokenizer converts text into token IDs
        ↓
because neural networks operate on numerical values rather than raw text
        ↓
the embedding layer converts those IDs into vectors
        ↓
those vectors can then be processed by transformer layers
```

The reader should understand the causal relationship, not only memorize the
sequence.

---

# 8. Explain What Changes and What Stays the Same

This is especially important for systems such as:

* LoRA
* fine-tuning
* caching
* quantization
* distributed inference
* configuration changes
* stateful applications

Explicitly state:

```text
What changes?
What remains unchanged?
```

Example for LoRA:

```text
Original model weights:
normally frozen

LoRA adapter weights:
trained

Inference:
base model + learned LoRA update
```

This prevents common misunderstandings.

---

# 9. Use Before-and-After Comparisons

Use before/after diagrams when a technology modifies an existing process.

Example:

```text
WITHOUT KV CACHE

Prompt tokens
↓
calculate K/V
↓
generate token
↓
process all previous tokens again
↓
calculate K/V again
↓
generate next token
```

versus:

```text
WITH KV CACHE

Prompt tokens
↓
calculate K/V once
↓
store them
↓
generate token
↓
reuse stored K/V
↓
calculate only new token's K/V
↓
generate next token
```

Then explain exactly what was saved.

---

# 10. Use Concrete Numerical Examples

When numbers would help, use actual values.

For example, when explaining LoRA:

```text
Original matrix:

4096 × 4096
= 16,777,216 parameters
```

If rank is 16:

```text
A:
16 × 4096
= 65,536

B:
4096 × 16
= 65,536

Total trainable LoRA parameters:
131,072
```

Then explain why this is much smaller than training all 16.7 million values.

Do not introduce unnecessary large examples when a small one can demonstrate
the same mechanism.

---

# 11. Explain Code From Outside In

When explaining code, do not immediately begin line by line.

First establish:

```text
What is this program/module/function trying to accomplish?
```

Then explain:

```text
Entry point
↓
Inputs
↓
Major components
↓
Execution flow
↓
State changes
↓
Outputs
```

Only after the overall flow is clear should important code sections be
explained individually.

---

# 12. Explain Functions by Their Contract

For an important function, explain:

```text
Purpose
Inputs
Output
Side effects
Dependencies
When it is called
What calls it next
```

Example:

```text
resolve_kpi(query)

Purpose:
Find the KPI definition matching a natural-language request.

Input:
query — user text such as "total data usage for the last 2 days"

Output:
the matching KPI configuration

Side effect:
none

Called by:
the request-handling layer before condition generation
```

Then explain the implementation.

---

# 13. Explain Variables by Their Role

Do not explain variables only by repeating their names.

Bad:

```text
candidate_scores contains candidate scores.
```

Better:

```text
candidate_scores stores how strongly each candidate KPI matches the user's
request.

A higher score means the resolver considers that candidate more relevant.
```

Explain why the value matters to later execution.

---

# 14. Explain Architecture as a Request Journey

When explaining an architecture, follow one request through the system.

For example:

```text
User
↓
Frontend
↓
API Gateway
↓
Authentication
↓
Application service
↓
Database
↓
LLM
↓
Response
```

For each component explain:

```text
What enters?
What does it do?
Why is it needed?
What does it produce?
Where does the result go?
```

Avoid architecture explanations that are just lists of technologies.

---

# 15. Separate Control Flow From Data Flow

When useful, distinguish:

```text
Control flow:
which component decides what happens next

Data flow:
what information moves between components
```

For example:

```text
Controller decides which service to call.
```

is control flow.

```text
The user ID is passed from the controller to the service.
```

is data flow.

Do not mix them when the distinction matters.

---

# 16. Explain State

For stateful systems, identify where information persists.

Examples include:

* database records
* files
* environment variables
* caches
* browser storage
* memory
* sessions
* queues
* model KV cache

Explain:

```text
Where is the state stored?
Who writes it?
Who reads it?
How long does it live?
When is it removed?
```

This is especially important for debugging.

---

# 17. Explain APIs as Conversations

Explain APIs as one system talking to another.

Use:

```text
Caller
↓
Request
↓
Server receives request
↓
Validation
↓
Business logic
↓
Data access / external service
↓
Response generation
↓
HTTP response
↓
Caller
```

Then introduce:

* HTTP method
* URL
* headers
* body
* authentication
* status code
* response payload

when relevant.

Show a small request/response example if useful.

---

# 18. Explain Networking as a Journey

For networking questions, trace the request.

For example:

```text
Application
↓
DNS lookup
↓
IP address
↓
TCP connection
↓
TLS handshake
↓
HTTP request
↓
Server
↓
Response
```

Explain only the layers relevant to the question, but establish the larger path
when necessary.

If the problem concerns a specific layer, clearly identify that layer.

---

# 19. Explain Databases From Query to Result

For database behavior, show the journey:

```text
Application
↓
SQL/query
↓
Database connection
↓
Query parser/planner
↓
Indexes / table access
↓
Rows retrieved
↓
Result returned
↓
Application
```

When explaining performance, distinguish:

* query design
* indexing
* amount of data
* network time
* locking
* transactions
* application-side processing

when relevant.

---

# 20. Explain Infrastructure as Layers

For infrastructure, identify the layers involved.

Example:

```text
Application
↓
Container
↓
Container runtime
↓
Operating system
↓
Virtual machine / physical server
↓
CPU / RAM / GPU / disk
```

For cloud systems, additional layers may include:

```text
Load balancer
↓
service
↓
container/orchestrator
↓
compute instance
↓
storage/database
```

Explain where responsibility changes between layers.

---

# 21. AI/ML Explanations Must Separate Training and Inference

Do not mix these two processes.

Use separate sections when relevant.

## Training

Explain:

```text
Training data
↓
forward pass
↓
prediction
↓
loss
↓
backpropagation
↓
gradients
↓
optimizer
↓
weight update
```

## Inference

Explain:

```text
Input
↓
forward pass
↓
output probabilities/logits
↓
selection/decoding
↓
result
```

Make clear that:

```text
training changes parameters
```

while normal inference usually does not.

---

# 22. Separate Pretraining, Fine-Tuning, and Inference

When discussing LLMs, distinguish:

```text
Pretraining
```

Learning general language/model capabilities from very large datasets.

```text
Fine-tuning
```

Further training an existing model for particular behavior or data.

```text
Inference
```

Using the trained model to produce outputs.

Do not treat these as interchangeable terms.

---

# 23. Explain Token Generation Step by Step

When discussing autoregressive LLM inference, establish that the model generally
generates one token at a time.

Use:

```text
Prompt
↓
model processes prompt
↓
logits for next token
↓
token selected
↓
token appended
↓
model processes next step
↓
another token selected
↓
repeat
```

Then introduce concepts such as:

* temperature
* top-p
* KV cache
* batching
* speculative decoding

in their correct place in this process.

---

# 24. Explain Attention With Roles Before Equations

Before showing attention formulas, establish the roles:

```text
Query:
what the current token is looking for

Key:
what each token says it contains

Value:
the information associated with that token
```

Then explain:

```text
Query compared with Keys
↓
attention scores
↓
scores normalized
↓
scores used to combine Values
↓
resulting contextual representation
```

Then, if appropriate, introduce:

```text
Attention(Q,K,V) = softmax(QKᵀ / √dₖ)V
```

Explain every symbol after the intuition is clear.

---

# 25. Explain LoRA as an Update, Not a Replacement

When explaining LoRA, make clear:

```text
Base weight:
W

Learned update:
ΔW

Effective weight:
W + ΔW
```

Explain that LoRA represents the update approximately using low-rank matrices:

```text
ΔW = B × A
```

Then explain:

* rank
* alpha/scaling
* which layers receive adapters
* what is trained
* what remains frozen
* how adapters are used or merged during inference

when relevant.

---

# 26. Explain Quantization as Representation Change

Do not say only:

```text
INT4 makes the model smaller.
```

Explain:

```text
Original model values
↓
represented with high precision
↓
quantization maps them to lower-precision representations
↓
less memory is required
↓
hardware can often process them more efficiently
```

Also explain the trade-off:

```text
lower memory / potentially higher speed
vs
possible accuracy degradation and implementation constraints
```

Distinguish weight quantization from activation or KV-cache quantization when
relevant.

---

# 27. Explain Caching by Showing Repeated Work

Caching becomes easier to understand by first identifying repeated work.

Use:

```text
Without cache:
calculate X
use X
discard X
need X again
calculate X again
```

versus:

```text
With cache:
calculate X
store X
need X again
reuse stored X
```

Then explain:

* what exactly is cached
* where it is stored
* when it is valid
* when it expires
* what invalidates it
* memory cost

when relevant.

---

# 28. Explain Parallelism by Showing Work Division

For multi-GPU or distributed systems, explain what work is being divided.

Distinguish when relevant:

```text
Data parallelism
```

Different batches/samples processed by model replicas.

```text
Tensor parallelism
```

Individual tensor operations split across devices.

```text
Pipeline parallelism
```

Different model layers placed on different devices/stages.

```text
Expert parallelism
```

Mixture-of-experts components distributed across devices.

Then show how communication happens between devices.

---

# 29. Explain Memory Consumption by Components

For GPU-memory questions, avoid giving only one total number.

Break memory into categories such as:

```text
Model weights
KV cache
activations
temporary buffers
CUDA/runtime overhead
optimizer states
gradients
LoRA/adapters
```

Specify which categories apply to:

```text
training
```

versus:

```text
inference
```

when relevant.

---

# 30. Explain Performance as a Bottleneck Problem

When explaining why something is slow, identify which resource limits the
system.

Potential bottlenecks include:

* CPU
* GPU compute
* GPU memory
* memory bandwidth
* network bandwidth
* disk I/O
* database queries
* serialization
* external APIs
* queueing
* synchronization

Explain how evidence points toward one bottleneck rather than assuming.

---

# 31. Explain Latency and Throughput Separately

When relevant, distinguish:

```text
Latency
```

How long one request takes.

```text
Throughput
```

How much work the system can complete over time.

A change may improve one while hurting the other.

For example, batching may improve throughput while increasing the waiting time
for an individual request.

---

# 32. Explain Configuration as Input to Behavior

Configuration should be explained as something the program reads to decide how
to behave.

Use:

```text
Configuration value
↓
program reads it
↓
program selects behavior
↓
visible result
```

For example:

```text
model="claude-sonnet"
↓
provider reads model setting
↓
request is constructed for that model
↓
that model handles the request
```

This is more useful than merely describing where the configuration file lives.

---

# 33. Explain Environment Variables Clearly

When environment variables matter, explain:

```text
Shell/process environment
↓
program starts
↓
program reads variable
↓
variable influences configuration
```

Clarify whether the variable is:

* set only for one command
* exported for the shell session
* stored persistently in shell configuration
* overridden by another layer

when relevant.

---

# 34. Explain Algorithms Using One Small Input

For algorithms, start with a tiny input.

Example:

```text
Input:
[5, 2, 8]
```

Walk through what the algorithm does at each step.

Then explain:

* why it works
* time complexity
* space complexity
* important edge cases

when relevant.

Do not start with Big-O notation before the user understands the algorithm.

---

# 35. Explain Mathematics From Meaning to Formula

Use:

```text
What problem are we solving?
↓
What quantity do we need?
↓
Meaning in words
↓
Formula
↓
Meaning of symbols
↓
Substitute numbers
↓
Calculate
↓
Interpret result
```

Example:

Before presenting cosine similarity:

```text
We want to measure how similar the direction of two vectors is, regardless of
their absolute length.
```

Then present the formula.

Do not let mathematical notation replace conceptual explanation.

---

# 36. Explain Trade-Offs Explicitly

Many engineering choices have no universally best option.

Show the trade-off.

Example:

```text
Larger batch
→ better GPU utilization
→ potentially higher throughput
→ more memory consumption
→ potentially higher request latency
```

Avoid calling one option "better" without explaining what metric is being
optimized.

---

# 37. Explain Why a Design Choice Exists

For important design decisions, answer:

```text
Why was this designed this way?
```

Possible reasons may include:

* performance
* memory
* maintainability
* isolation
* reliability
* scalability
* compatibility
* security
* latency
* cost

Do not invent motivations without evidence.

When the reason is inferred rather than documented, label it as an inference.

---

# 38. Distinguish Concept From Implementation

Make clear when explaining:

```text
concept
```

versus:

```text
one particular implementation
```

For example:

```text
RAG is the general pattern of retrieving external information and supplying it
to a model.

A specific LangChain implementation is one way to build that pattern.
```

This prevents the user from assuming a library-specific behavior defines the
entire concept.

---

# 39. Distinguish Logical and Physical Views

When relevant, separate:

```text
Logical view:
what components conceptually do
```

from:

```text
Physical view:
where those components actually run
```

For example:

```text
Logical:
API → model server → database

Physical:
API and model server may run on the same machine while the database runs on a
different host.
```

---

# 40. Explain Edge Cases After the Normal Case

Do not lead with every exception.

First establish the common path.

Then say:

```text
There is one important exception...
```

or:

```text
This changes when...
```

This preserves completeness without making the initial explanation confusing.

---

# 41. Preserve Exact Important Details

If the source material contains meaningful:

* dimensions
* model names
* versions
* ports
* paths
* parameter values
* limits
* timeouts
* error codes
* data sizes
* API fields

preserve them.

Explain what they mean instead of replacing them with vague language.

---

# 42. Use Tables Only When Comparison Benefits From Them

Tables are useful for comparisons such as:

| Concept   | What it changes             | When it happens |
| --------- | --------------------------- | --------------- |
| Training  | Model parameters            | During learning |
| Inference | Usually no model parameters | During usage    |

Do not use a table merely because information can technically fit inside one.

For sequential processes, arrows are usually clearer.

---

# 43. Avoid Unnecessary Jargon

Do not replace a simple word with a more academic term unless the technical
term matters.

Bad:

```text
The application instantiates an authentication context.
```

when:

```text
The application creates the authentication state it needs for this session.
```

would communicate more clearly.

When the technical term matters, include both.

---

# 44. Do Not Use "Basically" to Hide Complexity

Avoid explanations like:

```text
Basically, attention lets tokens communicate.
```

and stopping there.

It is acceptable as an opening intuition only if followed by the actual
mechanism.

The difficult part must eventually be explained.

---

# 45. Do Not Repeat the Same Explanation at Every Layer

Progressive explanation should add information.

Bad:

```text
Layer 1: KV cache stores previous values.
Layer 2: KV cache stores previous values.
Layer 3: KV cache stores previous values.
```

Better:

```text
Layer 1:
It remembers work the model already did.

Layer 2:
During token generation, earlier attention information is reused.

Layer 3:
The cached tensors are the keys and values produced by attention layers for
previous tokens.
```

Each layer should move the user forward.

---

# 46. End With the Complete Mental Model

For substantial explanations, finish by reconnecting the important pieces.

For example:

```text
Prompt
↓
tokens
↓
embeddings
↓
transformer layers
↓
attention
↓
logits
↓
next token
↓
repeat
```

Then briefly state what the specific concept contributes to that journey.

The user should leave with one coherent model rather than a collection of
isolated facts.

---

# Final Technical Explanation Check

Before finishing, verify that the explanation makes clear:

1. What is the concept or system?
2. What problem does it solve?
3. Why is it needed?
4. Where does it fit in the larger system?
5. What happens from beginning to end?
6. Why does each important step happen?
7. What technical terms matter?
8. What changes and what remains unchanged?
9. Is there a concrete example?
10. Are important numbers, parameters, or configurations preserved?
11. Are important exceptions or trade-offs explained?
12. Could a new person reconstruct the basic mechanism after reading the explanation?

If not, improve the explanation before finishing.
